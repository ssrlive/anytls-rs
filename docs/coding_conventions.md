# AnyTLS 多路复用编码约定

本文档用于约束 AnyTLS-RS 多路复用相关代码的实现与审核方式。
它不是协议扩展说明；协议已有定义以 [protocol.md](protocol.md) 为准。
本文把当前实现中必须保持的协议不变量、建议收敛的状态模型，以及用于验证实现的场景矩阵集中记录，供后续修改前审核。

## 使用原则

- 先证明协议不变量，再修改状态模型，最后用场景矩阵验证行为。
- 任何会改变 `Session`、`Stream`、帧路由、关闭传播或连接复用的修改，都必须说明受影响的不变量和场景。
- 状态转换应由拥有状态的对象执行：Session 管理会话和 Stream 表，Stream 管理自身读写方向与流级握手。
- 异步任务不能仅通过 Drop 推断协议状态；需要显式发送协议帧、设置本地状态并唤醒等待者。
- 网络 EOF、协议错误、对端 FIN 和本地关闭不是同一种事件，代码和测试不得混用这些概念。

## 第一阶段：明确协议不变量

以下规则是实现不可破坏的基础事实。

### 会话与控制流

1. 一条 TLS 连接对应一个 AnyTLS Session；Session 的接收循环和写入调度器属于 Session，不属于单个 Stream。
2. `sid == 0` 是控制流标识，只能承载协议规定的 Session 级命令，例如 SETTINGS、SERVER_SETTINGS、HEART 和 WASTE。
3. SYN、SYNACK、PSH、FIN 都是逻辑流命令，必须使用非零 SID。
   收到逻辑流命令的 `sid == 0` 时，Session 必须拒绝该协议输入并结束当前 Session。
4. Client 在新 Session 启动时先发送 SETTINGS；
   Server 在收到合法 SETTINGS 后才能接受 SYN，并在协议版本支持时发送 SERVER_SETTINGS。
5. 一个逻辑流的所有帧都按 SID 路由到同一个 Stream；未知 SID、重复建立同一 SID、以及不符合方向的帧
   必须按命令语义处理，不能静默创建错误状态。

### Stream ID

1. Client 在单个 Session 内为每个新 Stream 分配单调递增的非零 `u32` SID。
2. SID 分配不能回绕复用。计数器耗尽时，`open_stream` 必须返回错误；不得生成 SID 0，也不得覆盖仍在表中的 Stream。
3. `fetch_update` 返回更新前的值。若计数器以 `0` 初始化，生成逻辑必须使用递增后的值，首个 SID 应为 `1`。
4. 一个已经关闭并从表中移除的 SID，其迟到的 PSH/FIN/SYNACK 不得重新创建 Stream。
   对已取消本地 Stream 的迟到 SYNACK 可按客户端策略忽略，但必须有明确理由和测试覆盖。

### 数据与关闭顺序

1. 同一 Stream 中，已接收的 PSH 必须先于随后接收的 FIN 对本地读取方可见；FIN 不能丢弃此前排队的数据。
2. PSH 只传递数据，不改变 Stream 的打开状态；FIN 表示对端写方向结束，不等同于整个 Stream 或 Session 立即消失。
3. 本地读关闭、本地写关闭、对端 FIN、协议错误和 Session 终止必须分别传播到对应等待者。
4. Stream 只有在双方方向均已结束、发生不可恢复错误，或所属 Session 被终止后，才可从 Session 的活动表中移除。
5. Session 终止必须唤醒所有 Stream 的读、写、握手和背压等待者，并释放其占用的预算；不能留下永久等待的任务。

### 资源与调度

1. Session 接收循环不能因为某一个 Stream 的慢速读取而停止接收其他 Stream 的帧。
2. 入站数据和待发送数据必须受既定预算限制；Stream 关闭或 Session 终止时，相关预算必须释放。
3. 控制帧不能被无限数据帧饿死，数据帧也不能使控制帧队列无限增长。调度策略的改变必须用顺序和公平性场景验证。
4. 单个 Stream 的失败原则上不应无条件终止仍然有效的 Session；只有协议层或 TLS 层不可恢复的错误才终止整个 Session。

## 第二阶段：收敛状态模型

状态模型的目标是让每个事件只有一个明确归属、一个合法结果和一个清理路径。实现时应避免用多个布尔值组合出未经定义的隐含状态。

### Session 状态

Session 至少应能区分以下阶段：

| 阶段          | 允许的关键事件                       | 结束条件                     |
| ------------- | ------------------------------------ | ---------------------------- |
| `Created`     | 启动读写任务                         | 启动成功后进入 `Running`     |
| `Running`     | 合法控制帧、合法流帧、心跳、单流错误 | TLS EOF、协议错误、显式终止  |
| `Terminating` | 清理 Stream、唤醒等待者、停止 writer | 清理完成后进入 `Terminated`  |
| `Terminated`  | 仅允许幂等清理和查询                 | 不再接受新 Stream 或新协议帧 |

`SETTINGS` 是否已收到、对端协议版本和 writer 是否失败是 Session 的协议前置条件或终止原因，
不应通过“猜测当前阶段”来替代明确记录。

### Stream 状态

Stream 的建议模型如下：

| 维度       | 状态                               | 含义                                        |
| ---------- | ---------------------------------- | ------------------------------------------- |
| 流级握手   | `Pending` / `Succeeded` / `Failed` | SYN 已提交、SYNACK 成功或失败               |
| 本地写方向 | `Open` / `FinSent` / `Closed`      | 本地是否还可发送 PSH，以及 FIN 是否已发送   |
| 远端写方向 | `Open` / `FinReceived` / `Closed`  | 是否还可能收到 PSH，以及 FIN 后如何排空数据 |
| 生命周期   | `Active` / `Removed`               | 是否仍由 Session 表拥有                     |

上述维度可以在代码中使用现有字段表达，但每次修改必须写清楚事件对各维度的影响。例如：

- 本地 EOF：本地写方向进入 `FinSent`，发送一次 FIN；不应立即丢弃远端尚未读取的数据。
- 收到 FIN：远端写方向进入 `FinReceived`；先排空已排队 PSH，再向本地读取方返回 EOF。
- SYNACK 错误：流级握手进入 `Failed`，唤醒等待握手的调用方；不应仅因为单流失败而关闭整个 Session。
- Session 终止：所有 Stream 统一进入终止清理路径，未完成握手和阻塞 I/O 都必须得到错误或取消结果。
- 从 Session 表移除：必须保证不会再有新的帧路由到该 Stream；迟到帧只能按已定义策略忽略或拒绝。

### 修改检查项

修改状态逻辑时，提交说明或评审描述至少应回答：

- 事件从哪个对象进入，哪个对象拥有最终决策权？
- 事件前后的 Session 状态、Stream 握手状态和两个方向状态分别是什么？
- 哪些任务被唤醒，哪些通道/预算被释放？
- 重复事件、迟到事件和并发事件是否幂等？
- 该事件是单流错误还是 Session 错误？依据是什么？

## 第三阶段：用场景矩阵验证

每次改变 多路复用 核心逻辑后，至少执行与改动相关的单元测试，并用下表检查正常、边界和并发路径。
矩阵中的“预期结果”是行为约定；具体测试名称可以随实现调整。

| 场景           | 输入/操作                                  | 预期结果                                                        |
| -------------- | ------------------------------------------ | --------------------------------------------------------------- |
| 首个逻辑流     | 新建 Session，打开第一个 Stream            | SYN 使用 `sid=1`，不使用控制 SID 0                              |
| 连续分配       | 连续打开多个 Stream                        | SID 严格递增且非零，各 Stream 唯一                              |
| SID 耗尽       | 计数器接近 `u32::MAX` 后继续打开           | 返回耗尽错误，不回绕、不生成 0、不覆盖已有 Stream               |
| 控制流越界     | 收到 `SYN/PSH/FIN/SYNACK sid=0`            | 拒绝协议输入并终止当前 Session                                  |
| SYN 顺序错误   | SETTINGS 前收到 SYN                        | 拒绝该 Session；不创建 Stream                                   |
| 重复 SYN       | 对活动 SID 再次收到 SYN                    | 拒绝重复建立；原 Stream 状态不被覆盖                            |
| 未知流数据     | 收到未知 SID 的 PSH/FIN                    | 按协议策略拒绝或忽略；不得创建幽灵 Stream                       |
| 正常握手       | SYN 后收到成功 SYNACK                      | Pending -> Succeeded，打开方解除等待并可传输数据                |
| 流级握手失败   | SYN 后收到带错误信息的 SYNACK              | Pending -> Failed；调用方收到错误，Session 可继续复用           |
| PSH 后 FIN     | 连续收到 PSH、FIN                          | 读取方先读完 PSH，再收到 EOF                                    |
| FIN 后迟到数据 | 收到 FIN 后再收到同一流 PSH                | 按方向状态拒绝或按明确的迟到策略处理，不破坏其他流              |
| 本地半关闭     | 本地写入 EOF                               | 发送一次 FIN；仍可读取对端尚未发送完的数据                      |
| 双向关闭       | 双方各自发送/接收 FIN                      | Stream 清理一次并从活动表移除；Session 保持可用                 |
| 慢流背压       | 一个 Stream 不读取，另一个 Stream 持续收发 | 接收循环仍能处理其他流；预算达到上限时按背压工作                |
| 并发开流       | 多任务同时调用 `open_stream`               | 每个成功 Stream 获得唯一 SID；失败不会留下表项或悬挂握手        |
| 单流失败       | 一个 Stream 的目标连接失败                 | 该 Stream 的等待者收到错误；其他 Stream 和 Session 不被无故关闭 |
| Session 失败   | TLS EOF、writer 错误或协议错误             | 所有 Stream 被唤醒并清理；新开流失败；资源释放完成              |
| 迟到 SYNACK    | 本地 Stream 已取消后收到 SYNACK            | 不重新创建 Stream；按客户端策略忽略或记录可诊断日志             |
| Session 复用   | 最后一个 Stream 完成后再次发起请求         | 健康 Session 回到 idle pool，并能打开新的非零 SID Stream        |
| 空闲超时       | Idle Session 超过回收时间                  | Session 被关闭并从池中移除；不会影响其他活跃 Session            |

### 验证层级

1. **单元测试**：覆盖帧合法性、SID 规则、状态转换、Pipe 排序和资源释放。
2. **Session 集成测试**：使用内存或测试 I/O 验证多 Stream 交错、关闭传播和 Session 终止。
3. **烟测**：启动真实 server/client/backend，通过 SOCKS5 获取固定响应，确认首个 SYN、目标连接和回包完整。
4. **回归检查**：运行 `cargo test`；改动连接启动或协议兼容性时，再运行 `python -u scripts/smoke_test.py`。

烟测失败时，先删除旧日志再判断结果；日志必须能区分探测连接、正常 AnyTLS Session 和 curl 对应的 Session。
裸 TLS 探测可能制造没有 AnyTLS 认证或帧的连接，不应把它的错误当成正常代理请求失败。

## 审核记录

以下项目在实现继续演进前需要明确决策：

- Session 状态和 Stream 多维状态是否采用上面的命名与边界，还是映射到现有字段。
- 未知 SID、FIN 后迟到 PSH、迟到 SYNACK 的最终处理策略是“忽略并记录”还是“终止 Session”。
- 单流握手失败、目标连接失败是否始终隔离在单流范围内。
- `max_streams_per_session`、idle pool 和 Session 终止之间的权威状态来源。
- 哪些场景必须成为自动化回归测试，哪些只作为人工审核清单。

本节在审核完成前保留为待决策项；实现不应把待决策项默认为新的协议行为。
